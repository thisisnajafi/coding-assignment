# AI usage

## Tools

- **An AI coding assistant (agent mode)** working in my repository and terminal: it scaffolded the
  FastAPI backend and Next.js frontend, wrote most of the code and tests, ran them, built the Docker
  images and took the screenshots with Playwright. I defined the architecture, security rules,
  fallback behaviour and commit plan, and reviewed the output.
- **GapGPT (OpenAI-compatible API, `gpt-4o`)** inside the product for ticket triage.

## Where it helped

- Fast scaffolding (FastAPI routers, SQLAlchemy models, shadcn/ui components, RTL layout, Dockerfiles).
- Writing the offline test suite with a fake AI client, including edge cases I listed
  (invalid enums, timeouts, injection, masking).
- Persian UI text and the system prompt draft.

## Limitations / what I had to correct or check

- Pydantic `strict=True` with string enums rejected valid AI answers; caught by tests and changed to
  exact (case-sensitive) enum matching with `extra="forbid"`.
- The first secret-masking heuristic also masked HTML in the XSS sample ticket; adjusted so markup is
  kept as plain text and only password-like tokens are masked.
- The raw GapGPT model list was very long (dated snapshots, non-chat models); added filtering.
- Reasoning models reject a custom `temperature`, so it is only sent to classic chat models.
- Security decisions (404 for others' tickets, AI never changing state, masking before the AI call)
  were specified by me and verified with tests rather than trusted from generated code.
- Generated code needed review for consistency between the backend API contract and the frontend.

## Later extensions (same assistant)

- Skeleton loaders, UI polish, the message thread and the model combobox were generated by the
  assistant from my specs; I checked every change against the API contract and the tests.
- I asked it to verify each model in the picker with a real call through GapGPT, not just trust
  the `/models` list; all models now on the allowlist answered with valid JSON.
- The shadcn CLI asked interactively to overwrite existing components, so the `command` component
  was written by hand on top of `cmdk` (only `popover` came from the CLI).
- Thread-aware prompting needed explicit limits (character budget, oldest trimmed) and tag
  neutralisation; tests check the prompt contains the thread in order, masks secrets and has no
  other user's data.
- After I reviewed the IT screen, the assistant reworked it from my notes: a suggestion created
  after the final reply could not be sent, the final reply was shown twice, and pasted error text
  was faded and cut off. Each fix has a test (sending the suggestion, confirmation, the final-reply
  action hidden once a final reply exists).
- `PROMPTS.md` was generated from the real code (the system prompt copied word for word, and the example built with the actual masking and prompt functions), so the docs match what is sent.
- Security hardening was reviewed before merging: the assistant checked the existing rate limiter and headers instead of rewriting them, verified `npm audit` against the official npm registry (the local mirror has no audit endpoint), and added tests for each new secret pattern.
